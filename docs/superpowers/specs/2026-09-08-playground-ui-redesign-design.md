# Playground 加密数据生命周期页面重设计

> 状态：**已作废**（被 `2026-09-10-playground-person-crud-design.md` 取代）  
> 日期：2026-09-08  
> 页面：`/playground/`  
> 目的：让测试人员直观看到业务数据从明文写入、加密落库、摘要生成，到查询解密和完整性校验的完整生命周期。

---

## 1. 背景与问题

现有 Playground 按 CRUD、Digest、SQL、Complex、Multi-DS 分成独立标签页，适合调用单个接口，但不利于验证一条数据的完整处理链路：

- 新增、修改、查询和摘要操作彼此割裂；
- 结果区直接展示 JSON，无法快速区分请求明文、数据库密文和业务明文；
- `raw-query` 当前仅在响应中设置 `rawHint`，查询本身仍走普通拦截连接，不能保证展示数据库原始密文；
- SQL、复杂查询和多数据源能力与核心加解密测试并列，页面主次不清。

本次重设计将默认页面改为单记录、逐步骤的“加密数据生命周期”工作台。

## 2. 目标与非目标

### 2.1 目标

1. 围绕一条 `digest_user` 记录完成新增、查询、修改、再次查询、摘要校验和篡改验证。
2. 每一步固定展示三个视角：请求明文、数据库原始密文与摘要、业务查询解密结果。
3. 自动串联记录 ID 和步骤状态，使测试人员无需手工拼接操作。
4. 对加密、解密、摘要更新和篡改检测给出明确的通过或失败判断。
5. 保留 SQL、Complex、Multi-DS 能力，但降级到“更多测试”次级区域。

### 2.2 非目标

- 不替代 JUnit 和集成测试；
- 不开放任意 SQL；
- 不把 Playground 合并到 Monitor；
- 不允许普通业务操作直接写入摘要字段；
- 不在本次重设计中增加新的加密算法或摘要算法。

## 3. 核心数据模型

主流程固定使用 `digest_user`：

| 字段 | 页面用途 | 安全行为 |
|------|----------|----------|
| `id` | 串联同一次测试流程 | 数据库生成，新增成功后自动保存 |
| `name` | 用户姓名 | 写入加密，查询解密 |
| `phone` | 用户手机号 | 写入加密，查询解密，同时参与摘要 |
| `age` | 普通字段 | 明文存储，用作对照 |
| `email` | 普通字段 | 明文存储，用作对照 |
| `row_digest` | 完整性摘要 | 系统生成和更新，普通表单不可编辑 |

页面初始化时读取实际配置。如果 `digest_user` 不在白名单，或加密、摘要配置不满足上述模型，相关步骤应禁用并明确指出缺失项。

## 4. 页面信息架构

### 4.1 顶部栏

- 标题：加密数据生命周期；
- 当前数据源：单数据源时显示名称但不可切换，多数据源时提供选择；
- 当前流程记录 ID；
- “重置流程”按钮：仅清空页面状态，不删除数据库记录；
- Monitor 入口；
- “更多测试”入口。

### 4.2 流程导航

桌面端左侧展示六个有顺序的步骤；窄屏下移动到操作区上方并允许横向滚动：

1. 新增用户；
2. 查询并解密；
3. 修改敏感字段；
4. 再次查询；
5. 校验摘要；
6. 篡改并验证。

每个步骤具有未开始、可执行、执行中、成功、失败五种状态。新增成功前，后续步骤不可执行；已完成步骤可返回查看当时快照。

### 4.3 操作区

桌面端主内容位于流程导航右侧，上方是当前步骤操作区，下方是三视角结果区。操作区只展示当前步骤需要的输入和一个主操作：

- 新增：`name`、`phone`、`age`、`email`；
- 查询：使用当前记录 ID，无需重复输入；
- 修改：默认修改 `phone`，并允许同时修改其他业务字段；
- 再次查询：读取修改后的记录；
- 摘要校验：无业务输入，执行正常读取与校验；
- 篡改验证：选择篡改摘要或密文字段，二次确认后执行。

### 4.4 三视角结果区

结果区在桌面端采用三列、窄屏下采用单列纵向排列，并始终保持相同结构：

1. **请求明文**：本步骤提交的业务字段和值；
2. **数据库原始值**：绕过加解密拦截后读到的密文、普通字段和 `row_digest`；
3. **业务查询结果**：经过正常拦截链解密并完成摘要校验后的数据。

每个视角提供格式化展示和“查看原始 JSON”，但默认界面以字段对比为主。

### 4.5 更多测试

现有能力移入次级区域：

- SQL：跳转 Monitor；
- Complex：LIKE、分页、JOIN、批量插入；
- Multi-DS：各数据源行数对照。

次级区域不参与主流程步骤状态，也不占用默认页面首屏。

## 5. 生命周期数据流

### 5.1 新增用户

1. 页面提交明文业务字段；
2. 后端通过正常 securt-kit JDBC 拦截链执行 INSERT；
3. `name`、`phone` 加密后落库；
4. 系统根据明文 `phone` 生成 `row_digest`；
5. 后端分别读取原始库记录和正常业务记录；
6. 页面检查敏感字段密文不同于请求明文、摘要非空、业务查询值等于请求值。

### 5.2 查询并解密

1. 使用流程记录 ID 执行正常 SELECT；
2. 拦截链验证摘要并解密敏感字段；
3. 页面将业务结果与新增请求快照对比；
4. 值一致且摘要校验通过时，该步骤成功。

### 5.3 修改敏感字段

1. 页面提交新的业务字段，禁止提交 `row_digest`；
2. 后端通过正常拦截链执行 UPDATE；
3. 被修改的敏感字段重新加密，摘要根据最新明文重新生成；
4. 页面检查密文和摘要是否相对新增快照发生变化。

### 5.4 再次查询

正常查询修改后的记录。解密值必须等于最新输入值；数据库原始敏感字段仍不得等于明文。

### 5.5 校验摘要

通过正常读取触发摘要校验，并返回结构化校验状态。页面展示：

- 是否通过；
- 使用的摘要字段；
- 当前摘要值；
- 失败策略和错误信息。

### 5.6 篡改并验证

1. 用户选择篡改 `row_digest` 或一个密文字段；
2. 页面显示二次确认，明确该操作仅用于测试；
3. 专用测试动作绕过加解密和摘要重写，直接修改数据库原始值；
4. 随后执行正常业务读取；
5. 只有既定摘要失败策略被触发时，该步骤才判定成功。

## 6. 后端接口与响应契约

现有 Dispatcher 和 Engine 分层保持不变。主流程可复用底层 CRUD/Digest 方法，但页面接口应返回统一测试快照，避免前端自行拼接和推断。

建议的主流程接口：

```text
GET  /playground/api/lifecycle/preflight.json
POST /playground/api/lifecycle/insert.json
POST /playground/api/lifecycle/query.json
POST /playground/api/lifecycle/update.json
POST /playground/api/lifecycle/verify.json
POST /playground/api/lifecycle/tamper.json
```

生命周期接口不在服务端保存页面流程状态。“重置流程”只清空浏览器内的记录 ID、步骤状态和快照，不调用删除或重置接口。

统一响应数据：

```json
{
  "step": "insert",
  "status": "PASSED",
  "recordId": 101,
  "message": "新增成功，加密与摘要生成符合预期",
  "requestPlaintext": {},
  "rawDatabaseRow": {},
  "businessRow": {},
  "digestVerification": {
    "status": "PASSED",
    "sourceFields": ["phone"],
    "digestField": "row_digest"
  },
  "assertions": [],
  "error": null
}
```

### 6.1 原始数据库读取

原始读取必须使用项目既有 `SECURT_SKIP` 注释绕过 securt-kit 拦截链；不额外引入专用原始数据源。实现时应通过测试证明：

- 原始 `name`、`phone` 与请求明文不同；
- 普通业务查询能还原为请求明文；
- `rawHint` 只能作为响应元数据，不能作为已绕过拦截的依据。

### 6.2 安全边界

- 生命周期接口固定操作 `digest_user`，不接受客户端表名；
- 字段使用服务端白名单，不接受任意列名；
- 篡改接口只允许固定目标和固定操作类型；
- 所有数据库值使用预编译参数；
- 篡改操作保留二次确认和服务端警告日志。

## 7. 状态与错误处理

- 页面启动先执行 preflight，检查数据源、表白名单、字段和摘要配置；
- 执行失败时保留输入、记录 ID 和之前的成功快照；
- 技术异常默认折叠，主提示使用可操作的业务语言；
- 记录不存在时提示重新新增或重置流程；
- 数据源切换后自动开启新流程，避免跨数据源复用记录 ID；
- 未观察到加密、摘要未生成、修改后摘要未变化等情况均判定为失败，而不是仅显示接口调用成功；
- 摘要校验失败属于“校验摘要”步骤失败，但在“篡改并验证”步骤中，预期的校验失败代表测试通过。

## 8. 测试与验收

### 8.1 后端

1. 新增后原始敏感字段为密文、摘要非空，业务查询为明文；
2. 修改 `phone` 后密文和摘要均变化；
3. 再次查询返回最新明文；
4. 正常记录摘要校验通过；
5. 绕过拦截篡改摘要后，正常读取触发配置的失败策略；
6. 原始读取确实绕过解密；
7. 生命周期接口拒绝任意表名、列名和篡改目标；
8. Boot2 与 Boot3 测试工程行为一致；
9. 多数据源切换后，记录和流程状态相互隔离。

### 8.2 前端

1. 六步状态按依赖关系启用；
2. 新增成功后自动保存并显示记录 ID；
3. 三视角结果正确映射统一快照；
4. 失败后输入和历史快照不丢失；
5. 摘要失败在正常校验与篡改验证中呈现不同判定；
6. 重置不发起删除请求；
7. “更多测试”中的原能力仍可访问；
8. 窄屏下流程导航、操作区和结果区可纵向排列。

## 9. 实施边界

预计实施会修改：

- `securt-kit-playground` 的页面 HTML、CSS 和 JavaScript；
- `PlaygroundEngine`、Dispatcher 与必要 DTO；
- Playground 后端及前端相关测试；
- 四个测试工程中必要的配置或说明。

旧版设计文档 `2026-09-06-playground-ui-design.md` 保留，作为已实现版本的历史记录。本设计只描述重设计目标，不在此阶段修改生产代码。

## 10. 已确认决策

- 主结构采用单记录生命周期工作台；
- 主流程使用统一的 `digest_user` 数据；
- 结果采用请求明文、数据库原始值、业务解密结果三视角；
- 流程逐步手动执行，不提供一键运行全部；
- 主流程包含新增、查询、修改、再次查询、摘要校验、篡改验证；
- SQL、Complex、Multi-DS 收入“更多测试”；
- 重置流程不删除数据库记录。
